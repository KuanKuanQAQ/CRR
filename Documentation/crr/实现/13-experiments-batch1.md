## E2／E3-5　跨区域控制流转移的静态全扫描【W-64】

清单称这是「全文唯一一条可以被完全验证的安全性质」「投入产出比最高」。

### 先修了扫描器的一个 bug（**这条比结果本身重要**）

首次运行报告「发现 1 处绕过跳板的直接跨区域转移」：

```
0xffffffff81d91016: jle ffffffff81d9101e <ikaslr_st_mul_body+0xe>  [rand→other @ 0xe]
```

但源地址 `…1016` 与目标 `…101e` **都落在随机化区域 `[…1000, …107e)` 内**，本不该判为越界。
根因在目标地址的正则：

```python
TARGET = re.compile(r"\b0x([0-9a-f]+)\b")     # 旧：只匹配带 0x 的
```

x86 的 objdump 把**分支目标印成裸十六进制**（`jle  ffffffff81d9101e <sym+0xe>`），
而**符号偏移才带 `0x`**（`+0xe`）。于是它抓到的一直是**符号偏移**而非目标地址。后果有两面：

- **假阳性**：区域内分支被判成越界（上面这条）；
- **假阴性（更严重）**：外部代码跳进随机化区域时，`dst` 永远解析不成 `rand`，
  **真正的违规会被漏报**。而漏报正是这条安全性质最不能承受的方向。

已改为要求至少 6 位十六进制并取首个匹配（内核地址 16 位）。

### 修正后的结果

```
扫描的控制流转移指令总数      : 795,727
  其中直接转移                : 778,567
  其中间接转移                :  17,160
跨随机化边界的（直接）转移    : 0
  未经跳板（应为 0）          : 0
随机化区域内的间接转移（复核）: 3
```

**例外清单为空。** 区域内 3 处间接转移已逐条人工核对，全部是设计中的 `fixed_out` 协议：

| 地址 | 目标符号 | 角色 |
| --- | --- | --- |
| `…105f` | `ikaslr_out_enter` | 声明目标 + 白名单检查 |
| `…1063` | `ikaslr_rf_helper` | 真正的外部调用 |
| `…1071` | `ikaslr_out_leave` | 离开区域 |

同一函数里 `%r12 = ikaslr_rf_counter` 经 `movabs` 绝对寻址，印证 §3.4.3 的 x86 方案可行。

### 仍不覆盖的两类（清单要求单独交代）

工具本身已在输出中声明：**手写汇编**不经编译器 Pass；**运行时生成的代码**
（BPF JIT、alternative、static key、`text_poke`）编译期不存在。这两类需另行处理，
不能算进「例外清单为空」。

> **对正文**：§6.4 的表 6-3 可直接用上面的三个数，但**必须同时写明这两类不在扫描范围内**，
> 否则「例外为空」是被高估的结论。

## E3-1　代码索引更新量的收敛【W-33】

清单指出现有的 78.9% 是「4 个函数、19 处引用」的小样本，不能写进正文，且**必须按类型分列**。
两条都已解决——**不需要编译器 pass 生效**，直接从重定位算真实规模。

### 小样本（原型现状，仅作对照）

| | 值 |
| --- | ---: |
| 随机化函数数 | 4 |
| 传统方法要改的引用 | 19 |
| 本机制要改的 target 槽 | 4 |
| 收敛率 | 78.9% |

### 真实规模（`fs/` + `net/core/` + `mm/`，175 个 .o、6 354 个函数）

新脚本 `scripts/ikaslr/index_convergence_scale.py`。**按索引类型分列**：

| 索引类型 | 条目数 | 占比 |
| --- | ---: | ---: |
| 直接调用 | 8 435 | 62.1% |
| **函数指针表（数据节）** | **4 494** | **33.1%** |
| 其他 | 550 | 4.1% |
| 代码内取地址 | 96 | 0.7% |
| **合计（传统方法要改）** | **13 575** | |
| **target 槽（本机制要改）** | **3 211** | |

**收敛率 = 1 − 3 211/13 575 = 76.35%**

### 全内核引用口径（**正确口径**）

上表只数了**范围内部**的引用。但指针追踪类方法必须改写**全内核**指向随机化函数的每一处引用，
因此正确的分母是全树。同一范围、引用扫全部 2 958 个目标文件：

| 索引类型 | 条目数 | 占比 |
| --- | ---: | ---: |
| 直接调用 | 32 901 | 80.5% |
| **函数指针表（数据节）** | **5 892** | **14.4%** |
| 其他 | 1 896 | 4.6% |
| 代码内取地址 | 186 | 0.5% |
| **合计（传统方法要改）** | **40 875** | |
| **target 槽（本机制要改）** | **3 792** | |

**收敛率 = 1 − 3 792/40 875 = 90.72%**

引用最多的范围内函数：`kfree`(6 359)、`seq_printf`(1 892)、`kmalloc_trace`(1 743)、`__kmalloc`(1 033)。

> **口径决定数字**：同一份代码，只因「引用从哪里数」不同，收敛率就从 **76.4%**（仅范围内）
> 变成 **90.7%**（全内核）。正文必须写明用的是哪一个。**推荐用全内核口径**——
> 它才对应「传统方法实际要改写多少」。

> **一条方法学教训（值得记下）**：内核构建目录里有 `source` 符号链接指回源码树，
> `glob('**/*.o')` 会顺着它走出去。首次运行把 2 962 个目标文件放大成 **124 695** 个，
> 并把源码树里与本次构建无关的陈旧 `.o`（`boot/` 下的 rootfs 镜像）也算了进来，
> 得出虚高的 99.78%。脚本现按 realpath 去重并只保留构建目录内的文件。
> **凡是"扫全树"的统计都要先核对文件数**（`find <build> -name '*.o' | wc -l`）。

### 两点必须写进正文的口径

1. **返回地址不计入分母**。它是运行期产物、静态数不出来；而它恰恰是本机制**不需要改写**的一类
   （陈旧返回由陷阱兜底重定向，§3.4.7）。若计入，传统方法的分母只会更大、收敛率更高。
2. **「函数指针表」占三分之一**，这正是内核 `file_operations` 一类 ops 表。它是指针追踪类方法
   最难处理的一类（散布在数据段、无类型信息），本机制把它一并收敛到一个 target 槽——
   这一点值得在 §3.6.2 单独强调。

> **与 96.9% 的关系**：全内核口径实测 **90.7%**（平均每函数 10.8 处引用），
> 与中期报告的 96.9% 同量级但仍有差距；要到 96.9% 需平均约 32 处引用。
> 差距来自随机化范围的选取——范围内函数被引用得越多，收敛越显著。
> 正文引用这个百分比时**必须连同「随机化范围」与「平均每函数引用数」一起给**，
> 否则它没有定义。

## E3-2　跳板机制的微观开销【W-34】

`/proc/ikaslr/bench`，`IKASLR_STATS=n`（生产档），QEMU+KVM：

| 项 | 实测 |
| --- | ---: |
| A 直接调用 | 5 ns |
| B 经 target 槽间接调用 | 7 ns |
| C 完整 `fixed_in` | **107 ns** |
| D 白名单查询 | 11 ns |
| 间接转移开销 = B−A | **2 ns** |
| **进出计数开销 = C−B** | **100 ns** |

**结论方向与清单要求一致**：开销在**计数**而非间接转移。本次 `IKASLR_STATS=n`，
所以这 100 ns 是**活跃执行流集合追踪本身**（自旋锁 + 数组扫描），不是统计计数器。
真机多核有锁竞争，实际只会更差。

**仍缺**：跨区域调用在**真实负载**中的动态占比（需真机 `perf`）。静态占比已测得
**61.2%**（见 `12-got-codemodel-results.md` §4.3），可作上界参照。

## E3-3　单次随机化的时间分解【R-34】

已按清单要求把关键路径拆成三段（新增 `/proc/ikaslr/stats` 的 `cp_*` 字段）：

| 阶段 | 实测 | 说明 |
| --- | ---: | --- |
| 等待活跃集合清空 `cp_wait_ns` | 204 ns | 空闲时 |
| 更新 target 槽 `cp_update_ns` | 271 ns | **3 个函数** |
| **关键路径合计** `critical_path_ns` | **1 980 ns** | |
| 变体准备 `prepare_ns` | 178 µs | **在关键路径之外** |
| 改映射到陷阱镜像 `cp_remap_ns` | **28 486 ns** | **不在关键路径内**，见 E3-7 |

**判据核对（清单要求）**：关键路径应与**函数数**近似线性、与代码字节数无关。
`cp_update_ns` = 271 ns / 3 函数 ≈ 90 ns/函数，符合「每函数一个槽」的预期。
`cp_wait_ns` 与 `cp_remap_ns` 都与函数数无关，属固定开销。

> 中期报告的「平均 15.1 ms、95 分位 18.5 ms」是**变体池之前的数字，已作废**，勿沿用。

## E3-7　改映射与跨核 TLB 失效的代价【W-38】

这一项直接检验 §3.5.5 新实现的「预建陷阱镜像 + 切换时改映射」。

### 结果一：改映射是 **µs 级**，不是 ns 级

```
cp_remap_ns = 28 486 ns ≈ 28.5 µs
```

是关键路径其余部分（wait+update = 475 ns）的 **60 倍**。开销来自
`apply_to_existing_page_range` 遍历页表 + `flush_tlb_kernel_range` 的跨核 IPI。
QEMU 的 IPI 比真机贵，真机预计**单位数 µs**，但**量级仍是 µs**。

### 结果二：暴露窗口**并未消除**（修正此前的说法）

实际执行顺序是：

```c
ikaslr_live = next;  spin_unlock(...);
ikaslr_unblock_region();               /* ← 区域重新开放 */
WRITE_ONCE(ikaslr_last_ns, ...);       /* ← 关键路径计时到此为止 */
if (old && preemptible())
        ikaslr_retire_trap(old);       /* ← 改映射在这之后才发生 */
```

**改映射发生在 `unblock` 之后**，因此从 unblock 到 remap 完成之间（约 28.5 µs）：
区域已开放、旧变体仍是**有效可执行的旧代码**、陈旧返回不会陷入。
**此前「窗口即刻关死」的说法不成立**，改映射只是把窗口从「填充耗时」缩短到「改映射耗时」。

**两条可选处置**（需作者定夺）：

1. **把 `retire_trap` 移到 `unblock` 之前**——窗口内区域仍被阻断，代价是区域多阻断约 28.5 µs。
   注意这**不能完全消除**窗口：TLB 刷新完成前，其它核可能仍用旧 TLB 项执行旧代码。
2. **接受该窗口并如实写明其长度**（µs 级），论证其可利用性极低。

### 结果三：原子上下文**不可用**（清单要求给出明确结论）

`flush_tlb_kernel_range` 经 `on_each_cpu`／`smp_call_function` 发 IPI，**要求本地中断开启**；
关中断上下文调用会触发告警并有死锁风险。实现文档已记录同类事故：`set_memory_*` 的跨核 TLB
flush 在关中断且持有 VMCS 的上下文里破坏系统状态（随后 init 段错误）。

> **对 §3.4.6 的直接影响**：「就地完成」的条件必须收紧为**仅在可抢占上下文**；
> 原子上下文中随机化必须整体推迟。当前实现的 `if (old && preemptible())` 守卫与此一致，
> 但**正文需要把这条约束写明**，而不是含糊带过。
