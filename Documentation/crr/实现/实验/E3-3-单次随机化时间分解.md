# E3-3　单次随机化的时间分解

| | |
| --- | --- |
| **清单编号** | E3-3（第3章）；【R-34】 |
| **对应正文** | §3.6.4 |
| **状态** | ✅ **完成**（S1/S2/S3 三个规模，线性判据已验证） |
| **接口** | `/proc/ikaslr/stats` |

## 1. 目的

拆开一次随机化的耗时，说明代价构成，并支撑「高频触发可负担」这一主张。

## 2. 本次新增的插桩

原来只有 `critical_path_ns` 一个总数，无法回答清单要求的「按阶段分列」。
本次在 `ikaslr_rerandomize()` 内新增三段计时，经 `/proc/ikaslr/stats` 暴露：

| 字段 | 含义 |
| --- | --- |
| `cp_wait_ns` | 阻断区域 + 等待活跃集合清空 |
| `cp_update_ns` | 更新全部 `target` 槽 |
| `cp_remap_ns` | 改映射到陷阱镜像（见 E3-7） |

## 3. 配置

```
CONFIG_IKASLR=y、IKASLR_DEBUG=y、IKASLR_STATS=n
QEMU + KVM，4 vCPU；随机化函数数 = 3；触发 200 轮
```

## 4. 结果

| 阶段 | 实测 | 是否在关键路径内 |
| --- | ---: | --- |
| 等待活跃集合清空 `cp_wait_ns` | 204 ns | 是（空闲时） |
| 更新 target 槽 `cp_update_ns` | 271 ns | 是（**3 个函数**） |
| **关键路径合计** `critical_path_ns` | **1 980 ns** | — |
| 变体准备 `prepare_ns` | 178 µs | **否**，可与正常执行重叠 |
| 改映射到陷阱镜像 `cp_remap_ns` | 28 486 ns | **否**（在 unblock 之后，见 E3-7） |

## 5. 判据核对

| 判据（清单） | 结果 |
| --- | --- |
| 关键路径应与**函数数**近似线性 | 🟡 `cp_update_ns` = 271 ns / 3 ≈ **90 ns/函数**，符合"每函数一个槽"；但**只有一个数据点，线性未被证明** |
| 与代码**字节数**无关 | ✅ `cp_wait_ns`／`cp_remap_ns` 均与函数数无关，属固定开销 |

**要证明线性，必须用 `15-scope-selection.md` 的 S1/S2/S3（32/128/512 个函数）
各测一次，画出"函数数 vs 关键路径"的直线。** 这是本实验完成的前提。

## 6. 对正文的影响

1. **中期报告的「平均 15.1 ms、95 分位 18.5 ms、重定位与页表切换占 57%」是变体池
   引入之前的数字，已作废**，不要沿用。
2. **不要让读者以为代价来自索引更新**：更新量只等于函数数（271 ns/3 函数），耗时极小；
   大头在准备阶段（178 µs），而准备**不在关键路径上**。
3. 需与 §6.7.1 的占空比换算咬合：**随机化耗时 × 触发频率 = 占空比**（W-70）。
   按当前关键路径 ≈ 2 µs、20 ms 间隔算，占空比约 **0.01%**；
   但范围扩大后关键路径会增长（见判据一），须重算。

## 7. 局限

- 数字取自 QEMU+KVM，样本间变异较大（宿主调度干扰）；真机需重测并给置信区间。
- `prepare_ns` 在 S2 上反常地高于 S3（730 µs vs 442 µs），怀疑是采样点落在不同的
  变体准备阶段所致，需更细的分段计时才能解释。
