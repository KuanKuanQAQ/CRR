# E1　原型工程量统计

> 对应 `设计文档/草稿/实验总清单.md` §第4章 E1（论文 §6.3.1，W-61）。
> 数据由 `scripts/ikaslr/loc_stats.sh` 生成,可随代码演进重跑。
> 采集时间 2026-09-10,基线 `v6.8`(e8f897f4afef),当前 `topic/ikaslr`。

## 1. 目的

回答"你到底改了多少东西"。答辩几乎必问,且随代码演进会变,所以做成一条可重复
执行的脚本而不是一次性统计。

## 2. 口径:四类东西**不算**工程量

这一节比数字本身重要。相对 `v6.8`,本分支的 `git diff --stat` 是
**10 641 行插入**,但直接引用这个数会把工程量报虚一个量级:

| 类别 | 行数 | 为什么不算 |
|---|---:|---|
| `Documentation/crr/` 设计与实验文档 | 8 505 | 是本工作的产出,但不是"改了多少内核代码"的答案 |
| `samples/` 开发期样例 | 834 | 脚手架,不参与任何被评估的构建 |
| `boot/` 启动镜像脚本 | 314 | 同上 |
| **CKASLR 早期原型** | **322** | 更早的一个 syscall 驱动的重随机化原型(`kernel/rerand.c`、`rerand_utils.c`、`include/linux/rerand.h`、`fs/read_write.c` 里的 `rerand` 系统调用)。代码仍在树里,但 `CONFIG_CKASLR` 在**所有被评估的构建里都是 off**,不属于本文的实现 |

> CKASLR 这一条是复核时发现的。若不排除,工程量里会混进一个已被本方案取代的
> 原型,而它连编译都不参与。

## 3. 结果

### 3.1 总量

| 项 | 行数 |
|---|---:|
| 对既有内核文件的改动(23 个文件) | **+551 / −9** |
| 新增独立组件 | **8 582** |
| 　`kernel/ikaslr/`(运行时) | 4 776 |
| 　`scripts/ikaslr/`(实验脚本与静态分析) | 3 195 |
| 　`tools/ikaslr/`(编译器插件与 initramfs 程序) | 611 |
| **合计代码** | **≈ 9 133** |

"对既有内核文件的改动只有 551 行"是本方案的一个卖点:绝大部分逻辑在新增的独立
目录里,对内核既有代码的侵入很小。

### 3.2 编译器侧:按功能分列

`tools/ikaslr/llvm/IKaslrPass.cpp` 共 674 行(含注释;注释是本工作的一部分,
其中记录了多处必须那样写的理由)。按功能:

| 功能 | 行数 | 入口 |
|---|---:|---|
| 跳板生成与调用点重定向 | 108 | `transform()` |
| 函数级位置无关改造 | 58 | `makeBodyPositionIndependent()` |
| 绝对地址物化(含 arm64 字面量池) | 28 | `materializeAbs()` |
| `fixed_out` 序列与白名单生成 | 41 | `wrapOutboundCalls()` |
| 内建 `mem*` 降级 | 26 | `lowerMemIntrinsics()` |
| 跳板表项与 `target` 槽发射 | 40 | `emitTableEntry()` |
| 静态验证检查(`-ikaslr-verify`) | 26 | `verify()` |
| 不可改造函数的拒绝判定(变参/naked) | 16 | `rejectReason()` |

另有 GCC 插件 `tools/ikaslr/gcc/ikaslr_gcc.c` 324 行。

> **指针认证插桩(第 5 章)目前不在编译器插件里**,而是内核中的 C 函数由自测调用
> (`kernel/ikaslr/pacfi.c`)。清单 §E5-B(二)要求的"内联到每个间接调用点之后的
> 指令数与周期数"因此尚无数据 —— 这一栏在本表里如实留空,不能拿运行时 C 函数的
> 行数充作插桩工程量。

**流水线插入位置**(LLVM 新 Pass Manager,两个挂点):

| 挂点 | 做什么 | 为什么必须在这里 |
|---|---|---|
| `PipelineStart` | 给选中函数打 `noinline` | 必须在**内联器之前**。内联器一旦把它们内联,内联副本就绕过了跳板,不变式失效 |
| `OptimizerLast` | 做改造 | 在常规优化**之后**,否则优化会把跳板本身内联掉 |

**与 LTO 的关系**:本方案用 `-fpass-plugin` 在每个翻译单元内改造,不依赖 LTO。
若开 LTO,改造点会移到 LTO 阶段,跳板的 RAUW 语义不变(改名 + 全量替换使用者),
但届时"同一编译单元内的 static 函数"这一类别会消失,`fixed_out` 的分类需重测。

## 4. 顺带交代的两处编译器约束(原 W-31)

这两条若违反会**静默**破坏不变式,因此写进正文:

1. **被随机化的函数必须在内联优化之前标记 `noinline`。** 否则内联副本绕过跳板。
   实现:`IKaslrMarkPass` 挂在 `PipelineStart`。
2. **重定向必须先建跳板、RAUW、再改名落段。** 只改名是不够的 —— 调用指令引用的
   是函数**对象**而非名字,把原函数改名为 `F_body` 之后调用点会跟着指向 `F_body`,
   等于绕过跳板。实测确实如此(`caller_fn` 直接 `jmp target_fn_body`)。

## 5. 判据核对

清单未给 E1 定量判据(它是描述性统计)。可核对的是口径:

- ✅ 用 `git diff --stat` 对照基线 `v6.8`
- ✅ 排除纯格式改动(新增目录单独计,不进 diff)
- ✅ 按功能/子系统分列,而非只给总数
- ✅ 给出随机化范围各档规模

1. §6.3.1 的总量应写"**对既有内核代码的改动 551 行,新增组件约 8 600 行**",
   并说明文档与早期原型不计入。
2. "伙伴系统改动"这一栏要删 —— 本实现没有改伙伴系统。
3. 图 6-1 的方框面积按 §3.3 的分列取值;第 4、5 章的方框(1 182 / 414)明显小于
   第 3 章(约 1 900),这与"第 3 章是主体"的叙述一致。

   指令数/周期数也随之待做。
