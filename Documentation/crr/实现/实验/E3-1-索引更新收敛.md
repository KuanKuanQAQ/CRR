## S3 规模实测(481 个函数,x86-64,Linux 6.8)

映像:`+R` 生产配置(`IKASLR=y`、`STATS=n`、`DEBUG=n`),范围 S3。
工具:`scripts/ikaslr/index_convergence.py`(本次为它新增按类型分列的能力)。

### 结果

| 索引类型 | 传统方法每次随机化要改 | 本机制要改 |
|---|---:|---:|
| 代码中的直接转移 `call`/`jmp` | **13 588**(88.6%) | 0 |
| 代码中的取地址 `lea`/`movabs` | 438(2.9%) | 0 |
| 其他指令中出现的跳板地址 | 30(0.2%) | 0 |
| 数据中的函数指针(ops 表等) | **1 286**(8.4%) | 0 |
| GOT 项 | 0 | 0 |
| **`target` 槽** | — | **481** |
| **合计** | **15 342** | **481** |

**收敛率 = 1 − 481 / 15 342 = 96.9%**

### 判据核对

清单判据:"PIC + 跳板下需改写的条目数应**等于随机化函数个数**,与调用点总数无关"。

✅ **成立**:481 个 `target` 槽 = 481 个被随机化的函数,一一对应。
15 342 处引用中没有任何一处需要在随机化时改写 —— 它们全都指向**固定地址的跳板**。

### "剩下的 3.1% 是什么"(清单点名会被追问的)

就是那 **481 个 `target` 槽本身**。它不是"没收敛干净的残留",而是本机制
**不可约的每函数成本**:每个被随机化的函数必须有一处记录它当前在哪。
换句话说,收敛率随范围规模而变(函数越多、每函数的调用点越多,比值越低),
因此**报收敛率必须连同范围一起报**,单独一个百分比没有意义。

### 各类型的意义

- **直接转移占 88.6%** —— 这是跳板机制消除的主体。传统方案每次随机化要改写
  13 588 条 `call` 指令的立即数;本机制一条都不改。
- **数据中的函数指针占 8.4%** —— ops 表(`file_operations`、`net_device_ops` 等)。
  这一类**反汇编看不到**,必须单独扫数据段;早期只统计反汇编会漏掉它们。
- **GOT 项为 0** —— x86-64 用 `movabs` 绝对寻址,不需要 GOT(见
  `../16-position-independence.md`);arm64 是**随函数一起搬移**的字面量池,
  同样不需要在随机化时更新。
- **栈上的返回地址** —— 静态数不出来,它是运行时量。本机制**不把它算作索引更新**:
  退役变体整体填陷阱指令,陈旧返回由 `ikaslr_fixup_addr()` 重定向(§3.5.5),
  不需要遍历栈。压力测试中实测每轮有 3–16 次这样的修正,全部成功。

### 引用最多的函数(前 10)

| 函数 | 直接转移 | 取地址 | 数据指针 |
|---|---:|---:|---:|
| `seq_puts` | 480 | 10 | 1 |
| `__brelse` | 414 | 1 | 1 |
| `__folio_put` | 343 | 16 | 1 |
| `kvfree` | 289 | 9 | 1 |
| `skb_put` | 289 | 1 | 1 |
| `net_ratelimit` | 243 | 1 | 1 |

单个函数最多被 480 处直接调用 —— 传统方案随机化它一次就要改 480 处,
本机制改 1 处。这是 D1 最直观的一个例证。

### 与中期报告的对照

中期报告的大范围数字是 **96.9%**,本次 S3 规模实测**恰好一致**。
而 `../实验/` 早期记录的 78.9% 来自 4 个函数、19 处引用的小样本 —— 那个数字
**不能用**,规模差了三个数量级。

# E3-1　代码索引更新量的收敛（对应 D1）

| | |
| --- | --- |
| **清单编号** | E3-1（第3章）；【W-33】 |
| **对应正文** | §3.6.2 |
| **状态** | 🔵 **静态推算**（未经真实随机化验证） |
| **工具** | `scripts/ikaslr/index_convergence.py`（原型规模）、`scripts/ikaslr/index_convergence_scale.py`（真实规模，本次新写） |
| **原始输出** | `scripts/ikaslr/results/E3-1-*` |

## 1. 目的

证明一次随机化需要更新的代码索引数量**与随机化函数的调用点数量无关**，只与函数数量有关，
即从 O(n) 降到 O(1)。这是需求 D1 的直接证据，也是第 3 章立论的根基。

- 传统方法（指针追踪类）：必须改写**每一处**指向随机化函数的引用
- 本机制：每函数一个 `target` 槽，改写量 = **函数个数**
- 收敛率 = 1 − 函数数 ÷ 引用数

## 2. 为什么可以静态推算

「哪些引用指向随机化函数」完全由重定位决定，**不依赖编译器 pass 是否生效**。
因此在 pass 尚未铺开时，也能给出真实规模下的收敛率。
**但这只是"应该收敛到多少"的推算**，不等于"随机化后实测只改了 N 个槽"——
后者需 pass 生效后复测，见 §7 局限。

## 3. 配置

```
内核：Linux 6.8，x86_64_defconfig
范围：fs/ + net/core/ + mm/（175 个 .o，6 354 个函数符号）
口径：链接前 .o 的重定位
```

## 4. 步骤

```sh
make O=<b> CRR_TRAMPOLINE=n -j$(nproc) vmlinux fs/ net/core/ mm/
# 仅范围内引用
python3 scripts/ikaslr/index_convergence_scale.py --build-dir <b> \
        --objs 'fs/*.o' 'net/core/*.o' 'mm/*.o'
# 全内核引用（正确口径）
python3 scripts/ikaslr/index_convergence_scale.py --build-dir <b> \
        --objs 'fs/*.o' 'net/core/*.o' 'mm/*.o' --ref-objs '**/*.o'
```

## 5. 结果

### 5.1 原型规模（仅作对照，**不可写进正文**）

| | 值 |
| --- | ---: |
| 随机化函数数 | 4 |
| 传统方法要改的引用 | 19 |
| target 槽 | 4 |
| 收敛率 | 78.9% |

清单已指出这是「4 个函数、19 处引用」的小样本，不能作为结论。

### 5.2 真实规模，**按索引类型分列**（W-33 的硬要求）

**口径 A：仅数范围内部的引用**

| 索引类型 | 条目数 | 占比 |
| --- | ---: | ---: |
| 直接调用 | 8 435 | 62.1% |
| 函数指针表（数据节） | 4 494 | 33.1% |
| 其他 | 550 | 4.1% |
| 代码内取地址 | 96 | 0.7% |
| **合计** | **13 575** | |
| target 槽 | 3 211 | |

收敛率 = 1 − 3 211/13 575 = **76.35%**

**口径 B：数全内核的引用（推荐，2 958 个目标文件）**

| 索引类型 | 条目数 | 占比 |
| --- | ---: | ---: |
| 直接调用 | 32 901 | 80.5% |
| **函数指针表（数据节）** | **5 892** | **14.4%** |
| 其他 | 1 896 | 4.6% |
| 代码内取地址 | 186 | 0.5% |
| **合计（传统方法要改）** | **40 875** | |
| **target 槽（本机制要改）** | **3 792** | |

收敛率 = 1 − 3 792/40 875 = **90.72%**

引用最多的范围内函数：`kfree`(6 359)、`seq_printf`(1 892)、`kmalloc_trace`(1 743)、`__kmalloc`(1 033)。

## 6. 判据核对与口径

| 判据（清单） | 结果 |
| --- | --- |
| 需改写条目数 = 随机化函数个数 | ✅ 推算成立（3 792 槽 vs 40 875 引用） |
| 必须按类型分列 | ✅ 见上表 |

**两条必须写进正文的口径**：

1. **返回地址不计入分母**。它是运行期产物、静态数不出来；而它恰是本机制**不需要改写**
   的一类（陈旧返回由陷阱兜底重定向，§3.4.7）。若计入，传统方法分母只会更大、收敛率更高。
2. **口径决定数字**：同一份代码，只因「引用从哪里数」不同，收敛率就从 **76.4%**
   （仅范围内）变成 **90.7%**（全内核）。**推荐全内核口径**——它才对应"传统方法实际要
   改写多少"。正文必须写明用的是哪一个。

### 与中期报告 96.9% 的关系

全内核口径实测 **90.7%**（平均每函数 10.8 处引用），同量级但仍有差距；
要到 96.9% 需平均约 32 处引用。差距来自**随机化范围的选取**——范围内函数被引用得越多，
收敛越显著。**正文引用这个百分比时必须连同「随机化范围」与「平均每函数引用数」一起给**，
否则它没有定义。

> 参考：按 `15-scope-selection.md` 选出的 **S1**（32 个 VFS 核心函数）覆盖 4 503 处引用，
> 平均 **140.7 处/函数**，对应收敛率 **99.3%**。可见收敛率主要由**选谁**决定，
> 这也是为什么名单按引用数降序排。

## 7. 局限（必须如实写）

1. **这是静态推算，不是随机化后实测。** 真正验证 D1 需要 pass 生效后，
   在一次随机化中统计"实际改写了多少条索引"，并与 E3-5 的静态扫描交叉核对
   （若实际改写数 > 函数数，说明存在绕过跳板的索引）。
2. **函数指针表占 14%～33%**，正是内核 `file_operations` 一类 ops 表——
   指针追踪类方法最难处理的一类（散布在数据段、无类型信息）。本机制把它一并收敛到
   一个 target 槽，这一点值得在 §3.6.2 单独强调。

## 8. 一条方法学教训

首次跑全内核口径时得到虚高的 **99.78%**。原因：内核构建目录里有 `source` 符号链接指回
源码树，`glob('**/*.o')` 顺着它走出去，把 **2 962** 个目标文件放大成 **124 695** 个，
还把源码树里与本次构建无关的陈旧 `.o`（`boot/` 下的 rootfs 镜像）算了进来。
脚本现按 realpath 去重并只保留构建目录内的文件。
**凡"扫全树"的统计都要先核对文件数**（`find <build> -name '*.o' | wc -l`）。
