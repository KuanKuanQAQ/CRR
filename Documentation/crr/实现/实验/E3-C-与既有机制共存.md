# E3-C　与内核既有机制的共存(R-67)

> 对应 `设计文档/草稿/实验总清单.md` §第1章 E3-C(论文 §3.8)与 **R-67**。
> 清单标注:"**这是第 3 章最可能被追问的一处**"、"R-67 决定所有性能实验的配置"。
>
> 实测环境:x86-64,Linux 6.8,clang 14,S3 范围(480 个函数),QEMU+KVM。

## 1. 结论表

| 机制 | 是否受影响 | 具体表现 | 如何适配 | 功能损失 |
|---|---|---|---|---|
| **ftrace** | ⚠️ 运行期 | 静态构建**无冲突**;启用 tracer 时补丁打在映像地址上,**静默失效** | 需把 `__mcount_loc` 的地址翻译到当前变体,但那样写进去的 `call __fentry__` 会破坏可搬移性 | **有**:被随机化的函数无法被 ftrace 跟踪 |
| **kprobes** | ⚠️ 运行期 | 探**跳板**正常;探**函数体**注册成功但**一次不命中** | 同上 | **有**:同上 |
| **栈回溯** | ⚠️ 是 | ORC 表按地址索引,搬移后查不到;已强制改用帧指针 unwinder。回溯本身可用,但变体内的帧**无法符号化** | 改用帧指针(四档一律相同) | **有**:回溯里被随机化的帧显示为裸地址 |
| **livepatch** | ❌ 是 | 依赖 ftrace 的入口补丁 + 一致性模型要在栈上找被替换函数的地址 | 无 | **有**:被随机化的函数无法热补丁 |
| **static call** | ❌ 编不出来 | 写回的是指向区域外的 `call rel32` | 无解 | 含 static call 的函数**不能**进随机化范围 |
| `__ex_table` / `__bug_table` / `__jump_table` | ✅ 已解决 | 见 `../17-implementation-current.md` §3.7 | 查表时换算地址 / 母本传播 | 无 |

## 2. ftrace:一处需要更正的判断

**我起初把 ftrace 判成"与位置无关性本质冲突"、要求把含 `__mcount_loc` 的函数
全部排除。实测之后这个判断是错的。**

### 实测

开 `CONFIG_FUNCTION_TRACER=y` + `CONFIG_DYNAMIC_FTRACE=y` 编 S3 范围:

```
随机化区域 [0xffffffff81f01000,0xffffffff81f28914)  162068 B，函数体 480 个
✅ 全部可搬移：无指向区域外的 PC 相对引用
```

原因在函数入口:

```
ffffffff81f0f660 <dput_body>:
  f3 0f 1e fa          endbr64
  0f 1f 44 00 00       nopl   0x0(%rax,%rax,1)   ← ftrace 的补丁点，构建期是 NOP
  55                   push   %rbp
```

`DYNAMIC_FTRACE` 在**构建期**就把 `call __fentry__` 换成了 5 字节 NOP,
静态映像里根本没有那条 PC 相对调用。

### 真正的冲突点

`__mcount_loc` 共 **53 281** 条,其中 **477 条指向随机化区域**(480 个函数里的 477 个)。
运行期启用 tracer 时,ftrace 按表里的**映像地址**把 NOP 改成 `call __fentry__`。
而首次随机化之后,映像里的 `.rand.text` 已被置 NX、再也不会执行 —— 补丁打在了
一份死代码上,**当前变体完全不受影响**。

于是:

- **现状**:启用 tracer 对被随机化的函数**静默无效**。
- **若要让它生效**:必须把补丁翻译到当前变体。但写进去的 `call __fentry__` 是
  **指向区域外的 `call rel32`**,下一轮搬移就失效 —— 这才是本质不相容的地方,
  而它在"想让 ftrace 真的工作"时才出现,不在静态构建时出现。

### 由此的处置更正

`gen_funcs.py` 把 `__mcount_loc` 从**硬约束**里移出。理由:排除它会让开着 ftrace 的
内核**一个函数都不能随机化**(53 281 个插桩点覆盖几乎全部函数),而代价只是"被随机化
的函数不能被跟踪"这一功能损失。收益与代价严重不对等。

`.static_call_sites` 仍是硬约束 —— 它在**启动时**就把 `call rel32` 写进代码,
变体从母本复制之后偏移就是错的,`verify_movable.py` 会当场报出来。

## 3. kprobes:实测(`selftest.c` `test_kprobes_coexist`)

| 探什么 | `register_kprobe` | 随机化前命中 | 随机化后命中 |
|---|---|---:|---:|
| 跳板 `ikaslr_st_add` @ `0xffffffff81eb1004` | 成功 | **1** | **1** |
| 函数体 `ikaslr_st_add_body` @ `0xffffffff81eb9004`(映像地址) | **成功** | **0** | **0** |

函数体探针注册时,kallsyms 给出的是**映像里的**链接期地址,而当时的变体入口在
`0xffa0000000455640`。探针装在了永不执行的代码上。

> **`register_kprobe` 返回成功却一次不命中 —— 这是静默失效,比报错更糟**,
> 使用者会以为探针生效了。正文必须写清楚这一点。

一个可选的改进方向(未实现):在 `register_kprobe` 的路径上调用
`ikaslr_image_to_live()`,若地址落在随机化区域就**拒绝并返回 `-EINVAL`**,
把静默失效变成明确拒绝。这不解决功能损失,但消除了误导。

## 4. 栈回溯

- **ORC**:按地址索引,搬移后查不到条目。**已强制改用帧指针 unwinder**,四档一律
  相同(见 `../17-implementation-current.md` §4)。作者 2026-09-10 决定不做 ORC 重定位。
- **帧指针回溯**:链本身完整(跳板继承了 `frame-pointer` 属性),但变体地址不在
  `_stext.._etext` 内,`__kernel_text_address()` 返回假,因此**变体内的帧无法符号化**。
  实测的 oops 回溯里,被随机化的函数那几层显示为裸地址或被略去。

这是**可用性损失而非正确性损失**,但调试体验明显变差,正文要如实写。

## 5. R-67 的答复

清单说 R-67"决定所有性能实验的配置",两种可能的结论:

> 若结论是"互斥",所有性能实验必须在这些设施关闭的条件下进行并在第 6 章说明;
> 若"可共存",要补一组开启后的开销数据。

**实测结论是"可共存,但被随机化的函数会失去可观测性"** —— 既不是互斥,也不是
无损共存。因此:

1. **性能实验不必关闭 ftrace/kprobes**。它们开着也不影响随机化的正确性与可搬移性
   (已实测),因此不构成配置约束。
2. 但**四档必须一律相同**地设置它们 —— 否则测的是 ftrace 插桩本身的开销
   (每个函数入口 5 字节 NOP + `__mcount_loc` 表)而不是随机化开销。
   当前四档都是 `FUNCTION_TRACER=n`(defconfig 默认),口径一致。
3. 若要补"开启后的开销数据",那测的是 **ftrace 的常驻开销**,与本机制无关,
   建议不做。


## 7. 对正文的影响

1. §3.8 用 §1 的结论表,**逐行给出"是否受影响 / 表现 / 适配 / 功能损失"**。
2. **不要写"ftrace 与本机制互斥"** —— 静态构建无冲突,冲突在启用 tracer 时,
   且表现是静默失效而非崩溃。这个区分会被有内核背景的评委追问。
3. **静默失效要正面写**:`register_kprobe` 成功却不命中、`echo function >
   current_tracer` 对被随机化的函数无效。并给出"改为明确拒绝"的改进方向。
4. §6.3 的四档配置说明里补一句:ftrace/kprobes 四档一律相同,不构成配置约束。
