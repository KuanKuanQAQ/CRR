# 代码模型的实现设计，与「哪些内核代码不能被随机化」

> 回答两件事：**函数级位置无关代码在 x86-64 上怎么实现**（§3.4.3 的工程落地），
> 以及**由此导致哪些内核代码搬不动**——后者不是理论推演，是逐函数实测的结果。
> 统计脚本：`scripts/ikaslr/gen_funcs.py`。

---

## 1. 为什么基座必须是 `-mcmodel=kernel`

Linux x86-64 用的是**定制的内存模型**：内核代码与数据都被链接到地址空间**最高 2 GB**
（`0xffffffff80000000` 以上）。`-mcmodel=kernel` 正是为这个布局设计的——它假定所有
内核符号地址都能用**符号扩展的 32 位立即数**表示。整个内核的链接脚本、per-CPU 机制、
以及大量手写汇编都建立在这个假定之上。

因此**不能**把内核整体换成 `-mcmodel=large`。实测（`12-got-codemodel-results.md` §2.1）：
对 `fs/ net/core/ mm/` 175 个目标文件整目录加 `-mcmodel=large`，**只有 7 个编得过**。

**正确的做法是局部改造**：基座保持 `-mcmodel=kernel`，编译器插件只对**被选中随机化的
函数体**改变其对外引用的寻址方式，内核其余部分完全不受影响。

## 2. 函数级位置无关的实现（两个平台不同）

一个函数要能「整体搬到任意地址后仍然正确」，充要条件是：**函数体内不含任何指向区域外
的 PC 相对引用**。函数**内部**的相对跳转随函数整体搬移自动保持正确，不必处理。

区域外的引用只有两类，分别处理：

| 引用类型 | x86-64 的处理 | AArch64 的处理 |
| --- | --- | --- |
| **全局变量** | 64 位绝对立即数 `movabs $addr,%reg`（10 B），地址不随代码位置变 | `adrp` 是 PC 相对的**页寻址**，搬移后失效 → 改为经**共享全局偏移表**取址（`adrp :got:` + `ldr`） |
| **外部函数调用** | 改由 `fixed_out` 跳板处理（§3.4.3 优化一） | `bl` 是 PC 相对 ±128 MB 直接跳转，**无法随迁移保持正确** → 必须改为经偏移表/字面量池的**间接跳转**，同样归 `fixed_out` |

两个平台的实测印证：

- **x86**：`ikaslr_rf_general_body` 反汇编显示 `movabs $0xffffffff82f7ecc4,%r12`
  （即全局变量 `ikaslr_rf_counter`），以及 `call *%rax` 指向 `ikaslr_out_enter` /
  `ikaslr_out_leave`——绝对寻址 + `fixed_out`，与设计一致（见 `实验/E3-5-静态全扫描.md`）。
- **arm64**：共享偏移表是**刚需**而非优化。实测范围内有 **24 549 处外部调用站点**
  （每 19 条指令一次），全部必须改成间接（`12-got-codemodel-results.md` §4.3）。

> **x86 上共享偏移表只是体积优化**：全局变量已能用绝对立即数直接寻址，不必经表。
> 表的价值在 arm64。这一点两平台不对称，正文要分开写。

## 3. 由此导致的不可搬移代码（**实测**）

对函数体施加绝对寻址后，有三类内核构造会**编译失败**，另有一类会**运行错误**。
根因统一：它们都要求把**符号地址或偏移当成编译期 32 位立即数**——这正是
高 2 GB 模型能提供、而 64 位绝对寻址不能提供的东西。

| # | 构造 | 出处 | 约束形式 | 后果 | 可否回避 |
| --- | --- | --- | --- | --- | --- |
| 1 | **per-CPU 访问** | `asm/current.h` 的 `this_cpu_read_stable`，即 `current` | `%gs:%c[offset]`，percpu 偏移须为常量 | 汇编器报 `bad memory operand` | **不可**。percpu 是内核核心设施 |
| 2 | `BUG()`/`WARN()` | `asm/bug.h` 的 `_BUG_FLAGS` | `"i"(__FILE__)`，字符串**地址**作立即数 | 编译失败 | 可，关 `CONFIG_DEBUG_BUGVERBOSE`（失去文件名/行号） |
| 3 | 静态键 | `asm/jump_label.h` 的 `arch_static_branch` | `"i"(key)`，符号**地址**作立即数 | 编译失败 | 可，关 `CONFIG_JUMP_LABEL`（有性能代价） |
| 4 | **`__ex_table`** | 异常修正表 | 表项以代码地址为键 | **正确性错误**：本该 fixup 的缺页/用户拷贝异常变成 oops | 需运行时一并搬移表项 |

另有工具链级冲突：`-mcmodel=large` 与 retpoline 的 `-mindirect-branch=thunk-extern`
被 GCC 明确拒绝。

**验证过程**：关闭 2、3 之后编译错误从 223 降到 **0**，但汇编阶段仍因第 1 类失败。
这说明 2、3 是配置层面可回避的表层阻碍，**第 1 类才是真正的硬约束**。

### 还有一类：以代码地址为键的旁表

搬移函数会使这些表中指向它的表项失效：

| 旁表 | 失配后果 | 严重性 |
| --- | --- | --- |
| `__ex_table` | 异常 fixup 失配 → oops | **正确性** |
| `__bug_table` | `BUG()` 报告指向错误位置 | 功能 |
| `__jump_table` | 静态键改写打到错地址 | 功能 |
| `.altinstructions` | alternatives 改写失效 | 功能 |
| `.smp_locks` | SMP 锁前缀改写失效 | 功能 |
| `.orc_unwind_ip` | 栈回溯失效（oops/perf/livepatch） | 可观测性 |

> **ORC 要单独说**：它由 objtool 在**链接期**生成，`.o` 里没有，因此**不在下面的
> 逐函数统计内**；而它**覆盖几乎全部函数**。完整方案必须连 ORC 表项一起搬移。
> 正文引用下面的百分比时不能漏掉这一句。

## 4. 统计：到底有多少函数搬不动

`gen_funcs.py` 从目标文件的重定位里逐函数判定。样本 = `fs/` + `block/` + `net/core/` + `mm/`
（214 个目标文件，**7 469 个函数**，Linux 6.8 x86_64_defconfig）。

| 排除原因 | 函数数 | 占比 |
| --- | ---: | ---: |
| **per-CPU 访问**（不可回避） | **1 004** | **13.4%** |
| SMP 锁前缀改写 | 200 | 2.7% |
| `BUG()`/`WARN()` | 135 | 1.8% |
| 静态键 | 120 | 1.6% |
| alternatives | 20 | 0.3% |
| **`__ex_table`**（正确性） | **3** | **0.04%** |
| **合计不可搬移** | **1 482** | **19.8%** |
| **可搬移（合格）** | **5 987** | **80.2%** |

按子范围：

| 范围 | 函数数 | 不可搬移 | 占比 |
| --- | ---: | ---: | ---: |
| VFS 核心（10 个 .o） | 670 | 178 | **26.6%** |
| `fs/` 全部 | 2 102 | 434 | 20.6% |
| `fs/` + `block/` | 3 215 | 613 | 19.1% |
| `fs/`+`block/`+`net/core/`+`mm/` | 7 469 | 1 482 | 19.8% |
| **e1000/e1000e + nvme（驱动）** | 770 | 49 | **6.4%** |

### 三条值得写进正文的观察

1. **约五分之一的内建内核函数搬不动**，且**三分之二的排除来自 per-CPU 访问**
   （1 004/1 482）。`current` 几乎无处不在，这是 built-in 场景的固有门槛。
2. **越靠近核心，越搬不动**：VFS 核心 26.6% > `fs/` 全体 20.6% > 驱动 6.4%。
   这与直觉一致——核心路径更频繁地用 `current`、`BUG_ON`、静态键。
3. **驱动只有 6.4% 不可搬移**，明显低于内建核心代码。这从工程角度解释了
   **为什么 Adelie 一类方案选择只做模块/驱动**：它们回避掉的正是这 20% 的硬骨头。
   本文把范围推到 built-in，必须正面处理它——这既是代价，也是贡献。

### 处置策略

| 类别 | 处置 |
| --- | --- |
| per-CPU 访问 | **排除出随机化范围**。若要覆盖，需为 percpu 访问设计专门的重写（超出本文范围，列入未来工作） |
| `BUG()`/静态键 | 二选一：排除；或在随机化范围内关掉 `DEBUG_BUGVERBOSE`（**注意这会改变全内核配置**，四档必须一致） |
| `__ex_table` | 只有 3 个函数，**排除代价极低**，建议直接排除 |
| 旁表（bug/jump/alt/smp_locks） | 当前一并排除；完备方案应由插件+运行时搬移表项 |
| ORC | 全覆盖，无法靠排除解决，**必须搬移表项** |

## 5. 复现

```sh
python3 scripts/ikaslr/gen_funcs.py --build-dir <build> \
        --scope 'fs/*.o' 'block/*.o' 'net/core/*.o' 'mm/*.o' \
        --refs '**/*.o' --top 512 --out funcs.txt
```
输出同时给出排除统计与合格名单（按被引用次数降序）。
