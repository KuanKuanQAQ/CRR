### 0.2 两条口径（写任何性能数字前先确认）

1. **嵌套虚拟化把 VM exit 开销放大约 10 倍。** x86 EPT 路径实测约 18,000 周期／次退出，裸机约 1,000–2,000。凡涉及 EPT 退出频次的绝对开销，**必须取自裸机，或明确标注为嵌套环境下的悲观上界**。
2. **arm64 的 QEMU TCG 是纯软件模拟，绝对时间无意义。** 只用于验证功能正确性；性能一律以 ARM 真机为准。

### 0.3 两条报数纪律

- **统计开销单列。** 进出计数中"统计"本身值 70–90 ns，由独立的 `CONFIG_IKASLR_STATS` 控制。报开销必须写明是哪一档配置，否则数字无法比较。
- **小样本标注规模。** 例如现有 78.9% 的索引收敛来自 4 个函数，真实规模下才逼近 96.9%；不标规模等于没报。

## 第 1 章　第 3 章的实验（持续随机化执行机制）

**本章实验只回答第 3.3 节的三条设计需求。配置：仅启用第 3 章机制**，第 4、5 章关闭，否则测出的跳板开销里混入其他机制的成本。

### E3-1　代码索引更新量的收敛（§3.6.2，对应 D1）　【W-33】　状态：部分

**目的。** 证明一次随机化需要更新的代码索引数量与随机化函数的**调用点数量无关**，只与函数数量有关，即从 O(n) 降到 O(1)。这是需求 D1 的直接证据，也是全章立论的根基。

**自变量。** 三种配置：原始代码 / 仅启用函数级 PIC / PIC + 跳板。

**因变量。** 一次随机化中必须改写的索引条目数，**按索引类型分列**：直接调用、间接调用、返回地址、函数指针、GOT 项。

**步骤。**
1. 选定随机化范围（`funcs.txt`），先用小范围跑通流程，再扩到真实规模。
2. 对三种配置各编译一次内核，保留 `.o` 与 `vmlinux`。
3. 跑 `scripts/ikaslr/index_convergence.py`，它从重定位与反汇编中统计各类索引的数量。
4. 分别统计"存在多少条指向随机化函数的索引"与"随机化时实际需要改写多少条"。

**产出。** 一张表：行为索引类型，列为三种配置，格子里是条目数；末行给总计与相对原始配置的降幅。

**判据。** PIC + 跳板配置下，需改写的条目数应等于**随机化函数的个数**（每函数一个 `target_addr`），与调用点总数无关。若不等，说明存在绕过跳板的索引，应与 E6-2 的静态扫描结果交叉核对。

**坑。**
- 现有的 **78.9% 是 4 个函数、19 处引用的小样本**，不能直接写进正文。中期报告的 96.9% 是大范围下的数字，两者要在同一范围下重测才可比。
- **必须按类型分列。** 只报一个总百分比，评委会问"剩下的 3.1% 是什么"，那正是没有被消除的那一类索引，要能说清它是什么、为什么留着。

### E3-2　跳板机制的微观开销（§3.6.3）　【W-34】　状态：完成（数字待裸机复测）

**目的。** 给出经跳板的跨区域调用相对直接调用的额外周期数，并**拆开**成三部分，说明代价究竟花在哪里。

**已有结果（QEMU+KVM，2 vCPU，每档 200,000 次）。**

| 配置 | 间接转移 | 进出计数 | 跳板合计 | 白名单查询 |
| --- | ---: | ---: | ---: | ---: |
| `IKASLR_STATS=y` | 2 ns | 130 ns | 133 ns | 10 ns |
| `IKASLR_STATS=n`（生产） | 2 ns | 100 ns | **102 ns** | 12 ns |

**步骤。** `/proc/ikaslr/bench`（需 `CONFIG_IKASLR_DEBUG`）内置四档：A 直接调用等价函数、B 经 target 槽间接调用但不计数、C 完整 `fixed_in`、D 单次白名单查询。间接转移开销 = B−A，计数开销 = C−B。

**仍需补的（W-34）。** **跨区域调用在真实负载中的占比**。微观开销乘以占比才是实际影响。做法：在 LMBench / fio / netperf 负载下用 `perf` 采样统计经 `fixed_in`／`fixed_out` 的调用次数占全部间接调用的比例。

**产出。** 上表（裸机版）+ 一句"在 X 负载下跨区域调用占全部间接调用的 Y%，故实际影响约为 102 ns × Y%"。

**判据。** 结论方向必须是"**开销在计数而非间接转移**"。若正文只强调"多一次间接跳转的代价"，方向就写错了。

**坑。**
- **微基准会被编译器优化掉。** 首次实现时基线档 200,000 次只花 119 ns，因为被测函数是纯函数、参数为常量、结果未使用，循环被整个删除。修法：输入取自 `volatile` 变量、结果写回该变量，形成真实数据依赖。**做任何微基准前先自查这一条。**
- `wake_up()` 曾是最大单项（224→133 ns）。已改为 `wq_has_sleeper()` 判断后再唤醒，复测时确认这条优化仍在。
- **这一项一次做完可用两处**：占比同时是 §5.6.3「PA 验证次数减少」论断的依据（R-53）。

### E3-3　单次随机化的时间分解（§3.6.4）　【R-34】　状态：完成（待扩规模）

**目的。** 拆开一次随机化的耗时，说明代价的构成，并支撑"高频触发可负担"这一主张。

**已有结果。** 关键路径 **560 ns**（零分配）；变体准备 18–50 µs，位于关键路径**之外**且可与正常执行重叠。变体池引入前关键路径为 3.6–12.7 ms，相差约四个数量级。

**步骤。** 读 `/proc/ikaslr/stats` 的 `critical_path_ns` 与 `prepare_ns`；用 `trigger-loop.sh` 驱动多轮取分布。

**产出。** **按"关键路径"与"准备"两栏分列**的表，每栏再细分：关键路径含等待活跃集合清空、更新 `target_addr`、改映射到陷阱镜像；准备含布局生成、代码页排布与重定位、陷阱镜像生成、置权限。

**判据。** 关键路径耗时应与随机化函数数量近似线性（每函数一个槽 + 一次映射改写），与**代码字节数无关**。若与字节数相关，说明有逐字节操作漏在关键路径上。

**坑。**
- 中期报告的"平均 15.1 ms、95 分位 18.5 ms、重定位与页表切换占 57%"是**变体池之前的数字，已作废**，不要沿用。
- **不要让读者以为代价来自索引更新**：更新量只等于函数数，耗时极小；大头在准备阶段，而准备阶段不在关键路径上。
- 需与 §6.7.1 的占空比换算咬合：随机化耗时 × 触发频率 = 占空比（W-70）。

### E3-4　无副本性质的验证（§3.6.5，对应 D3）　【W-35】　状态：完成（工具就绪，待全量）

**目的。** 证明随机化之后内核地址空间中**不存在旧代码的可执行副本**。这是与 Shuffler 路线的关键区别，也是"随机化使已泄露信息过期"这一论证的前提。

**步骤。**
1. 触发若干轮随机化。
2. 扫描内核地址空间中所有可执行页，确认：映像内 `.rand.text` 已置 NX；已退役的变体已被改映射到陷阱镜像，其中已迁移函数的字节区间全为陷阱指令。
3. 对每个随机化函数，确认全局只有一份可执行副本。

**产出。** 一份清单：可执行页总数、属于随机化区域的页数、每个函数的可执行副本数（应恒为 1）；以及与保留副本方案的暴露窗口长度对比。

**判据。** 每函数可执行副本数 = 1。出现 >1 即无副本性质不成立。

**坑。** 首次随机化时旧份在内核映像里，**必须显式置 NX**，否则映像中那份旧代码仍可执行、随机化形同虚设。这一步曾被遗漏。

### E3-5　跨区域控制流转移的静态全扫描（§3.6.5、§6.4）　【W-35／W-64／E2】　状态：本机可做，**建议最先做**

**目的。** 机械验证"编译产物中不存在绕过跳板的跨区域控制流转移"。**这是全文唯一一条可以被完全验证的安全性质**，第 2.7 节不变式 I1 与 I3 都以它为前提。投入产出比最高。

**步骤。**
```sh
scripts/ikaslr/scan_xregion.py vmlinux            # 全量反汇编扫描
```
扫描器遍历所有代码，找出目标落在随机化区域内、而来源不在跳板区的控制流转移指令。

**产出。** 三个数：扫描到的跨区域转移指令总数、经由跳板的数量、**例外清单**（应为空）。第 3 章给方法与随机化范围内的结果，第 6 章给完整内核映像的结果。

**判据。** 例外清单为空。**若非空，逐条说明**：是手写汇编、是运行时生成的代码（如 eBPF、ftrace trampoline）、还是编译器遗漏。前两类要给出单独的处理方式，第三类是 bug。

**坑。**
- **最可能的遗漏正是手写汇编与运行时生成的代码**，编译器 pass 覆盖不到它们。扫描器要能识别并单列这两类，而不是笼统报"有 N 处例外"。
- arm64 的解析需要真实 arm64 映像验证过（x86 逻辑已验证）。

### E3-6　非抢占上下文的覆盖（§3.6.6，对应 D3）　【W-36】　状态：部分

**目的。** 说明推迟随机化机制在真实负载下的行为：多久推迟一次、推迟多长、有没有超时或死锁。

**因变量。** 推迟触发次数占全部触发的比例；推迟时长分布（给分位数，不只给均值）；最长推迟时长；超时与死锁计数。

**步骤。** 在真实负载（LMBench、fio、netperf）下开 `+R` 或 `+RD` 档，用 `trigger-loop.sh` 或第 4 章的检测驱动触发，读 `/proc/ikaslr/stats` 中的推迟计数与窗口统计。

**产出。** 一张推迟时长的分布图（CDF 或直方图）+ 一行超时／死锁计数（应为 0）。

**判据。** 最长推迟时长应显著小于第 1.1.5 节引用的 1.5–3.5 秒随机化间隔上界，否则推迟本身会破坏时效性。

**坑。**
- 现有的 1273 ns / 3181 ns 是**自测中"请求后立即 flush"测出的下界**，不代表真实负载下的分布，不能直接用。
- 中期报告中"一次系统调用的延迟平均约为几十毫秒"这一表述**明显有误**（正常应在微秒量级），若沿用会被当场质疑。
- 可复用中期报告的 `Img/cf_leave.pdf`（控制流离开当前函数的时间分布，约 90% 的函数在 100 ns 内离开）作为推迟窗口的上界依据。

### E3-7　改映射与跨核 TLB 失效的代价（§3.5.5）　【W-38】　状态：待真机

**目的。** 陷阱镜像的切换靠改写页映射实现，而改映射需要使其它核上的 TLB 项失效。要回答两个问题：它在关键路径上值多少时间？它在原子上下文中能不能安全使用？

**步骤。**
1. 在关键路径上对"改映射 + 跨核失效"单独计时，与 E3-3 的其余各项并列。
2. 在多核负载下触发随机化，观察跨核失效的处理器间中断对其它核的干扰。
3. 在关中断上下文中尝试执行改映射，确认是否安全。

**产出。** 加入 E3-3 时间分解表的一行；以及一个明确结论："原子上下文可用／不可用"。

**判据与后续。** 若原子上下文不可用，则 §3.4.6 的"就地完成"条件必须收紧（只在可抢占上下文完成），或把改映射交给推迟路径。**这直接决定 §3.4.6 分流策略的适用范围**，必须给出结论而不是含糊带过。

**坑。** 实现文档已记录：`set_memory_*` 的跨核 TLB flush 走处理器间中断，在关中断且持有 VMCS 的上下文里会破坏系统状态（实测导致随后 init 段错误）。改映射很可能有同样的约束。

### E3-8　编译器 Pass 的工程量与位置（§3.5.1）　【W-31】　状态：本机可做

**目的。** 交代 LLVM 与 GCC 两份插件的工程量、在编译流水线中的确切插入位置、以及与 LTO 的关系。第 5 章的 PA 插桩在此基础上扩展，因此接口要交代清楚。

**产出。** Pass 数量与代码行数（按功能分列：函数级 PIC 转换、跳板生成与控制流重定向、指针认证插桩、静态验证检查）；插入位置（哪个 pass 之后）；与 LTO 是否兼容。

**坑。** 两处会静默破坏不变式的设计约束必须写明：其一，被随机化函数必须在**内联优化之前**标记 `noinline`，否则内联出的副本既不经跳板也不计数；其二，重定向必须**先建跳板、RAUW、再改名落段**，只改名会让调用点跟着指向函数体、反而绕过跳板。

### E3-9　共享 GOT 规模与缓存行为（§3.4.3）　【R-31】　状态：本机可做

**目的。** 回填中期报告的"共享 GOT 后从数百 KB 降至约 8 KB、L1 命中率保持 97% 以上"，并量化大代码模型与共享 GOT 各自的代价。

**完整方案见 `got-codemodel-howto.md`**（四档编译配置 C0–C3、五个测试项 T1–T5、命令与记录模板）。要点：

- **T1 GOT 规模**：两种方案的表项数都能从**同一份构建的重定位信息**算出（每函数去重求和 vs 跨函数全局去重），不必编译两遍。
- **T2 体积膨胀**：`-mcmodel=kernel` vs `large -fno-pic`，比较 `.text` 总量与每函数均值。
- **T3 缓存**：**必须把 I-cache 与 D-cache 分开报**。代码膨胀压的是前者，共享表的集中访问压的是后者，混报会让两项代价互相掩盖。
- **T4 GOT 访问频度**；**T5 端到端影响**。

**三处口径必须写明**，否则数字没有定义：①"数百 KB"对应哪种朴素方案（每函数一张还是每编译单元一张）；② 命中率是 I 还是 D；③ 表项统计在链接前还是关掉链接器松弛之后。

### E3-10　与内核既有机制的共存（§3.8）　【W-37】　状态：待做

**目的。** 逐项交代函数级 PIC 与跳板改造对 `ftrace`、`kprobes`、栈回溯、`livepatch` 的影响。**这是本章最可能被追问的一处**：有内核背景的评委一定会问"你动了代码布局，ftrace 还能用吗"。

**产出。** 一张表，每行一个机制，列为：是否受影响、影响的具体表现、如何适配、是否有功能损失。

**与 R-67 的关系。** 若结论是"互斥"，则所有性能实验必须在这些设施关闭的条件下进行，并在第 6 章明确说明；若"可共存"，则要补一组开启后的开销数据。**这个选择要早做，因为它决定实验配置。**

## 第 2 章　第 4 章的实验（信息泄露检测与按需触发）

**配置：启用第 3 章 + 本章机制，关闭第 5 章的 PA 验证。** 第 3 章必须启用，因为本章的随机化动作由它执行。这与第 3 章实验（仅启用第 3 章）不同，需在正文写明。

**攻击行为一律由内核内受控自测驱动**，不引入任何向用户态暴露内核读写的载体（该含漏洞模块已永久移除）。

### E4-1　只执行内存的有效性（§4.5.1）　状态：完成（x86 单核）

**目的。** 证明代码页被置为只执行之后，对它的读取确实会被硬件捕获，且捕获的是精确的那一页。

**已有结果。** guest 读 execute-only 页触发 EPT violation，`gpa` 与被保护页精确一致、`qual=0x1a1`（读访问且该页不可读）；检测式循环（读 → 检测 → MTF 单步放行这一次 → 恢复只执行）5 次读全部捕获。

**仍需补的。** ARM 观察点路径的对应验证（需真机）：单个观察点覆盖整个随机化区域 + 跳板区域，读取触发、取指不触发。

**判据。** 读触发、执行不触发。若取指也触发，说明配置成了普通断点而非数据观察点。

**坑。** x86 上要先查 `IA32_VMX_EPT_VPID_CAP` 的 execute-only 能力位：不支持时 R=0,X=1 是非法组合，会得到 EPT misconfiguration（reason 49）而不是 violation，两者要分开处理。

### E4-2　检测覆盖率（§4.6.2，对应 D1）　【W-43】　状态：部分

**目的。** 说明三个检测源各自能覆盖攻击者的哪些探测行为、各自的覆盖率是多少。

**关键：不做"综合召回率"。** 中期报告曾用"XOM 检测率 100%、执行推测 98.2%、控制流异常 99.0%"三个数字连乘得到 99.98%。这有两处错误：其一，`1−(1−1.0)(1−0.982)(1−0.99)` 首项为零、整式恒等于 1，与所报的 99.98% 对不上；其二，**三个检测源并不独立**——同一种规避手法（不读代码、不引发崩溃、不产生异常控制流）会同时让三者失效，因此不能按独立事件连乘。

**正确做法。** **分源报告**，每源给出：它针对哪一类攻击者动作、在受控自测下的检出率、以及**它明确不覆盖的情形**。

**产出。** 一张表：行为三个检测源，列为"针对的攻击向量 / 检出率 / 不覆盖的情形"。外加一段文字，列出三源**共同**不覆盖的途径：经 `/proc/kallsyms` 一类内核自身导出的接口获取地址、微架构侧信道推测。这两类在 §2.6.4 已列为排除项，此处要呼应。

**坑。** 检出率的分母必须写明是"受控自测发起的探测次数"，不是"真实攻击中的探测次数"——后者本文没有样本。

### E4-3　误报率（§4.6.3，对应 D2）　【W-44】　状态：待真机

**目的。** 测出内核**自身**的合法代码读取有多少、会不会把它们误判为攻击。`kprobes`、`ftrace`、`livepatch`、栈回溯、`/proc/kcore` 等都会正常地读取代码。

**这项实验替代中期报告的"合法代码读取的有界性"引理。** 该引理断言"合法读取路径有限且可枚举，可通过静态分析识别"，但这恰恰是**需要实证的命题，不能作为前提**。本节要给出的是真实负载下的实测清单与误报率，不是一个断言。

**步骤。**
1. 在 Base 档跑一组代表性负载（启动、LMBench、fio、netperf、模块加载卸载、开关 ftrace/kprobes）。
2. 在 +RD 档跑同样的负载，记录每一次检测触发。
3. 人工归类每次触发：是内核自身的合法读取（误报），还是受控自测发起的探测（真报）。

**产出。** ①一份**合法读取来源清单**（哪个子系统、什么场景、频次）；②误报率 = 误报次数 ÷ 总触发次数；③每类误报的处置方式（白名单化、还是靠控制流审计过滤掉）。

**判据。** 误报若导致随机化频繁触发，就会变成可用性问题（随机化风暴）。误报率高时要能说清是靠审计策略挡住的还是靠白名单挡住的。

### E4-4　控制流审计的正确性（§4.4.4）　状态：完成

**目的。** 验证审计判据能区分"正常的整函数调用"与"跳进函数中间的 gadget 使用"。

**已有结果。** 入口（偏移为零）判为放行不触发，中部（偏移大于零）判为 gadget 并触发随机化；8 次压力测试全通过；x86（`int3`）与 arm64（`BRK`）双平台一致。

**仍需补的。** LBR／BRBE 的来源指令精确分类（当前用偏移判据落地核心区分）。补上之后可支持四类判定表中依赖指令类型的那两行，特别是"返回指令连续多次返回被探测函数才触发"。

**坑。** 偏移判据是**保守方向**：它可能把"返回到函数入口"型的复用误判为正常，代价是漏触发而非误触发。这一点要如实写，不能声称四类判定表已全部实现。

### E4-5　单次检测与审计的处理开销（§4.6.4）　状态：待真机

**目的。** 给出一次检测（异常捕获 → 定位 → 标记 → 恢复权限）与一次审计（陷阱 → 判定 → 重定向）的处理时间。

### E4-6　触发频率与触发延迟分布（§4.6.5，对应 D3）　【W-45】　状态：待真机

**目的。** 回答"检测到攻击行为之后，多久能完成一次随机化使已泄露的地址失效"，并与攻击者凑齐可用 gadget 所需的时间对比。

**这组实验替代中期报告的"及时随机化保证"定理。** 方法参照 Wang 等人对 JIT-ROP 场景下 gadget 收敛速度的测量：在内核负载上测出攻击者凑齐**足以完成攻击链**的 gadget 集合所需的时间，与本机制的触发延迟对比。**这是可测量、可复现、可被他人验证的形式，比一条定理有力得多。**

**因变量。** ①正常负载下的实测触发频率（机制自己产出了多少次随机化）；②从首次检测到随机化完成的延迟分布；③受控自测下攻击者凑齐可用 gadget 所需时间。

**产出。** 把 ② 与 ③ 的分布画在同一张图上，②的尾部应落在③的左侧。

**判据。** 触发延迟的**尾部**（95／99 分位）而非均值，必须小于攻击者凑齐 gadget 的时间。安全性由最坏情况决定。

**与第 6 章的分工。** 本章报的是"机制在给定负载下自己产出了多少次触发"，第 6.7.1 节报的是"人为设定频率下系统能承受多少"，两者问的不是同一件事，不算重复。

### E5-1　CFI 精度（§5.6.2，对应 D1）　【W-52】　状态：完成（口径待收紧）

**目的。** 用等价类大小说明本文机制相对 kCFI 与落地点标记类机制的精度提升。

**已有结果（Linux 6.8）。**

| 机制 | 划分依据 | 等价类个数 | 最大等价类 | 平均 |
| --- | --- | ---: | ---: | ---: |
| CET-IBT（封印后） | 有无 `endbr64` | 1 | 8,907（defconfig）／38,180（完整配置） | — |
| kCFI | 函数类型哈希 | 17,883 | **2,139** | 3.16 |
| 本文机制 | 调用点唯一上下文 | ≈调用点数 | **1** | 1 |

最大的几个等价类：`int (*)(void)` 2,139、`void (*)(void)` 2,069、`long (*)(struct device*, struct device_attribute*, char*)` 1,266。

**仍需补的两项（W-52）。**
1. **收紧口径**：当前用途径 A（DWARF 原型），统计的是"所有有实体的函数"，而 kCFI 等价类只应含**可能被间接调用**的函数，因此分母偏大、等价类偏大。收紧办法：只统计地址被取过的函数。若能用 Clang ≥16 构建，改用途径 B（`__kcfi_typeid_` 符号）更贴近编译器实际划分。
2. **本文机制的分布**：当前的"等价类=1"是**设计性质**，已在 arm64 机制级验证；全内核规模的分布需编译器 PA 插桩全量应用后统计。

**做一次回填三处。** §1.1.4（W-03）、§2.5.3（W-15）、§5.6.2。

**判据。** 论证的落点必须是**最大等价类**而非平均值。kCFI 平均只有 3.16，看起来很好，但决定安全性的是那个 2,139：一个 `int (*)(void)` 类型的间接调用在 kCFI 下有两千余个合法目标。

### E5-3　PA 机制的微观开销（§5.6.4）　状态：待真机

**目的。** 给出签名与认证指令本身的开销、上下文计算的开销、以及 `fixed_out` 处双重检查（PA 验证 + 白名单查询）的合计开销。

### E5-4　上下文计算的插桩开销（§5.5.2）　【W-54】　状态：待全量插桩

**目的。** 当前原型中签名／认证／验证是内核中的 C 函数、由自测调用，现算哈希的开销可忽略。但**内联到每一个间接调用点之后**，"每次间接调用多几条哈希指令"与"预先算好放在寄存器里"之间重新成为代码生成上的取舍。

**要测的。** 每个间接调用点因上下文计算而增加的指令数与周期数。

**一条可能的出路。** 调用点地址在编译期已知，其上下文原则上**可以在编译期算出并作为立即数嵌入**，这样运行时开销降为零。若实测指令数不可接受，这是第一个该试的方向。

**这一项是本节结论从原型推广到全量部署的必要证据。**

### E5-5　高扇入函数识别的收敛与准确性（§5.6.5）　【W-53】　状态：机制已验证，数据待测

**目的。** 两件事：识别需要多久收敛；识别得准不准。

**机制已验证。** arm64 实测：单调用点认领后多次调用不误判；第二个调用点触及判高扇入；篡改指针被 CFI 拒绝；定稿把单归属函数升为调用点唯一上下文。

**要测的两项。**
1. **收敛曲线**：从启动开始，"已建立唯一上下文的调用点比例"随时间上升的曲线，标出启动完成的位置。
2. **准确性（W-53，容易被忽略但必须做）**：与静态分析得到的"真实"高扇入函数集合对比，报告**漏识别**与**误识别**的比例。

**为什么准确性必须报。** 运行时识别只能发现**实际被执行到的路径**，冷路径上的高扇入函数不会被发现。**这是本方法的固有局限**，只报收敛曲线而不报漏识别率，等于回避了这个问题。漏识别的后果是：某个实际高扇入的函数被当作单归属函数定稿为唯一上下文，日后另一个调用点触及时会被判为 CFI violation（误杀）。

**产出。** 收敛曲线一张；准确性表一张（真实集合大小、识别出的数量、漏识别数与比例、误识别数与比例）。

### E5-6　跨区域劫持的拦截验证（§5.6.6）　状态：完成

**目的。** 验证 `fixed_out` 的双重检查能拒绝被伪造的跨区域转移，即防御 V4-B。

**已有结果。** arm64 实测：合法目标通过、篡改目标被拒绝。

**驱动方式。** 由内核内受控自测构造一个被篡改（或以错误上下文签名）的跨区域转移目标，观测是否被拒绝。**不引入任何用户态攻击载体。**

**仍可补的。** 分别测两项检查各自的拦截能力：只有白名单（无 PA）时能拦住什么、只有 PA（无白名单）时能拦住什么、两者都开时能拦住什么。这能说明"双重检查"不是冗余——白名单查的是集合成员性，PA 查的是来源真实性，二者不可互相替代。

### E5-7　PACMAN 前提的确认（§5.7.2）　【R-54】　状态：需确认表述

**目的。** 本章的安全论证以"攻击者无法获得 PA 验证预言机"为**显式前提**。中期报告曾把三种攻击策略（暴力破解、重用已有 PAC、上下文碰撞）列举后取最大值，并写"每次尝试都会触发 CFI violation"——**PACMAN 恰恰证明不会**：验证结果可经推测执行侧信道读出，攻击者可在不产生崩溃、不留日志的前提下爆破签名。

**要做的。** 确认正文改写后的条件性陈述与实际方案一致；把该前提及其脆弱性在讨论节单独说明，不要藏在论证里。

### E11　综合攻击链拦截（§6.8）　【W-72／73／74】　状态：改口径

**真实 CVE 端到端复现不做。** 它需要一个可运行的漏洞利用载体，与已移除的含漏洞模块同属两用攻击代码。**改由内核内受控自测驱动**：攻击者从威胁模型设定的起点（已具备任意读写）出发，该起点由受控自测直接赋予。

**这不影响结论的有效性**：三项机制拦截的是攻击者获得任意读写**之后**的每一步，而威胁模型本就假设攻击者已具备任意读写；从真实漏洞打入属于前置阶段，不改变机制在其后每一步的拦截行为。

**W-72　拦截矩阵。** 把攻击链分解为若干步骤，逐步标出在各档配置下被哪个机制拦截。**第一行是攻击者的起点而非被防御的步骤**，四档下都"成立"。逐列填写的意义在于**显示每个机制各自拦住了哪一步**，而不只给出"攻击失败"这一个结论。若某步在 +RDP 下仍成功而攻击最终仍失败，**也要如实标注**，并说明是后续哪一步拦住的。

**W-73　攻击者可用资源的收敛。** 三组数据，**均报分布而非均值**（安全性由最坏情况决定，均值会掩盖尾部）：拦截前获得的 gadget 数量（与表 2-1 的静态基线对照）、触发拦截所需的探测次数、从首次探测到拦截的时间。

**W-74　地址有效期（建议作为本节主要结论指标）。** 一个被泄露的代码地址从泄露到失效之间的时长。方法：在攻击链执行过程中记录每一个被泄露的地址及其失效时刻，给出有效期分布，与 1.5–3.5 秒的间隔上界对照。**这一指标比 gadget 计数更贴近本文的防御原理**——本文不减少 gadget 数量，改变的是它们地址的稳定性。

### E12　开销来源归因（§6.9）　【W-75】　状态：待 E3–E7

**目的。** 把端到端开销拆回具体来源：跳板间接跳转、执行流追踪的计数、白名单查询、检测机制的异常处理、随机化本身的暂停与迁移、PAC 指令。

**方法。** 用性能计数器或采样剖析给出各来源占比，与 §3.6.3、§4.6.4、§5.6.4 的微观测量对照。

**判据（本节的真正价值）。** **若端到端开销显著高于各微观开销之和，要解释差额来自何处**——例如缓存局部性的损失或页表压力。这类二阶效应只有在系统级才观察得到，**如实报告反而是本章的价值所在**。

### R-66　长时间运行的漂移（§6.10）　状态：并行挂着跑

**目的。** 跑数小时到数天的负载，观察随机化区域的地址空间占用、跳板表规模、触发频率是否随时间漂移，并提前发现内存泄漏一类问题。

**不难做**（挂一个负载生成器让它跑着即可），占日历时间但不占人力，**建议在别的实验做完之后挂上去**。很能说明系统的工程成熟度。

| 项 | 状态 | 正文该怎么写 |

| LBR 精确来源分类 | 待做（增强） | 说明当前用偏移判据落地了四类判定表的**核心区分**，指令类型的精确分类作为增强列出，如实说明未启用 |
| gadget 数量上界论断（R-41） | **已撤** | 正文已删。替代：审计把单个被探测函数上可完成的转移次数限制为常数 + 实测 gadget 可用性分布 + 触发延迟与间隔上界对比 |
| 「合法读取有界性」引理 | **已撤** | 替代为 E4-3 的实测清单与误报率 |
| 「及时随机化保证」定理 | **已撤** | 替代为 E4-6 的触发延迟分布 vs gadget 收敛速度对比 |
