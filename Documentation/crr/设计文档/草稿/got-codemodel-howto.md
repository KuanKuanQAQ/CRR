# 共享全局偏移表与大代码模型：测量方案与代价分析

> 回填论文 §3.4.3 的 **R-31**（中期报告称"共享 GOT 后总大小从数百 KB 降至约 8 KB、
> L1 缓存命中率保持在 97% 以上"，需在 Linux 6.8 上重测），并回答两个必须正面交代的问题：
> **`-mcmodel=large` 有什么弊端？共用一张全局偏移表有什么弊端？**
> 体例参照 `cfi-precision-howto.md`。所有命令以 x86-64 为主，arm64 差异单列。

## 2. T1　GOT 表项数与字节数（回答 R-31）

### 关键洞察：两种方案都可以从**同一份构建**的重定位信息算出来，不必真的编译两遍

- **每函数一张 GOT** 的总表项数 = Σ<sub>函数 f</sub>（f 引用到的**不同**全局符号数）
- **全局共享一张 GOT** 的总表项数 = 随机化范围内**所有**函数引用到的**不同**全局符号数（全局去重）

前者按函数去重，后者跨函数去重，差值即共享带来的节省。两者都能从目标文件的重定位表直接统计。

### 方法

```sh
# 1) 以 C3 配置编译随机化范围内的目标文件（保留 .o，不要 strip）
#    x86 关注 R_X86_64_GOTPCREL / GOTPCRELX；arm64 关注 R_AARCH64_ADR_GOT_PAGE / LD64_GOT_LO12_NC

# 2) 导出「函数 -> 被引用的全局符号」列表
for o in $(find . -name '*.o' -path '*<随机化范围>*'); do
    readelf -r --wide "$o"
done > relocs.txt

# 3) 统计（脚本见下）
scripts/ikaslr/got_stats.py --objs '<随机化范围>/**/*.o' --arch x86_64
```

`got_stats.py` 需要做的事（若尚未实现，按此写）：

1. 用 `readelf -r --wide` 或 pyelftools 读每个 `.o` 的重定位节；
2. 按重定位所在的节（`.text.<func>`）把重定位归属到函数；
3. 只保留 GOT 类重定位与指向**全局数据符号**的重定位（排除函数符号，因为 §3.4.3 优化一
   已把外部函数移出 GOT，交给 `fixed_out`）；
4. 输出三个数：
   - `per_func_total` = Σ 每函数去重后的符号数
   - `shared_total` = 全局去重后的符号数
   - `dedup_ratio` = 1 − shared_total / per_func_total

### 指标与记录模板

| 项 | 每函数一张（C2） | 全局共享（C3） | 节省 |
| --- | ---: | ---: | ---: |
| 表项数 | | | |
| 字节数（表项数 × 8） | | | |
| 随机化函数数 | | — | |
| 被引用的不同全局变量数 | — | | |

> **核对点。** `shared_total × 8 B` 就是共享 GOT 的字节数。若它落在 8 KB 附近，
> 则对应约 1000 个不同的全局变量，这个量级对若干个内核子系统而言是合理的。
> **中期报告"数百 KB"的那一侧要说清是哪种朴素方案**（每函数一张 GOT，还是每编译单元一张），
> 否则"降到 8 KB"这个对比没有定义。这是 R-31 必须补的口径。

### 坑

- **不要在链接后的 `vmlinux` 上数 `.got` 节大小**：内核静态链接后 GOT 可能被合并、
  优化或根本不生成独立节，链接前的 `.o` 重定位才是可靠来源。
- **`GOTPCRELX` 会被链接器松弛（relaxation）成直接寻址**，从而不占 GOT 表项。
  统计时要么在链接前统计（上游口径），要么用 `-Wl,--no-relax` 关掉松弛后再看链接产物。
  两个口径都合理，但**必须在正文写明用的是哪个**。
- 头文件里的 `static` 变量会在多个编译单元各自生成副本，去重时按 `符号名 + 定义位置` 判断，
  不要只按名字。

## 3. T2　代码体积膨胀（`-mcmodel=large` 的直接代价）

### 方法

同一份源码，分别以 C0 与 C1 编译，比较随机化范围内的代码量。

```sh
# 总量
size -A vmlinux | grep -E '\.text|\.rand\.text'

# 逐函数大小，便于算均值与分布
nm --print-size --size-sort --radix=d vmlinux | grep -F ' t ' > sizes.txt

# 单条引用的增量：反汇编数指令
objdump -d --no-show-raw-insn vmlinux \
  | awk '/<函数名>:/,/^$/' | grep -cE 'movabs|call \*'
```

### 指标

| 项 | C0（kernel 模型） | C1（large + fno-pic） | 增量 |
| --- | ---: | ---: | ---: |
| 随机化范围 `.text` 总字节 | | | |
| 随机化函数数 | | | |
| 每函数平均字节 | | | |
| 每次全局变量引用的字节数 | 约 6～7 | 10 | |
| 每次外部调用的字节数 | 5（`call rel32`） | 12～13（`movabs` + `call *reg`） | |

**预期量级**：`movabs $imm64, %reg` 占 10 字节，而 `mov <sym>(%rip), %reg` 约 6～7 字节；
外部调用由 5 字节的 `call rel32` 变成 `movabs`（10）+ `call *%reg`（2～3）。因此膨胀幅度
**与代码中外部引用的密度成正比**，引用密集的胶水函数膨胀最明显。报告时给出分布而非只给均值。

## 4. T3／T4　缓存、TLB 与 GOT 访问频度

### T3 方法（**必须把 I-cache 与 D-cache 分开报**）

中期报告只说"L1 缓存命中率 97%"，没说是指令还是数据。这两者受影响的机理完全不同：
代码膨胀（`-mcmodel=large`）压的是 **I-cache**，共享 GOT 的集中访问压的是 **D-cache**。
混在一起报，等于把两项代价互相掩盖。

```sh
# x86-64
perf stat -e L1-icache-load-misses,L1-dcache-loads,L1-dcache-load-misses,\
iTLB-load-misses,dTLB-load-misses,instructions,cycles \
    -- <负载>

# arm64（事件名不同）
perf stat -e l1i_cache,l1i_cache_refill,l1d_cache,l1d_cache_refill,\
l1i_tlb_refill,l1d_tlb_refill,instructions,cycles -- <负载>
```

负载取**会走随机化代码路径**的那些：`lat_syscall`、`fio randread-4k`、`netperf TCP_RR`。
纯用户态计算负载测不出内核代码布局的变化。

| 配置 | I-cache miss 率 | D-cache miss 率 | iTLB miss 率 | IPC |
| --- | ---: | ---: | ---: | ---: |
| C0 基线 | | | | |
| C1 large | | | | |
| C3 共享 GOT | | | | |

### T4 方法：GOT 访问的动态频度

静态数出随机化代码中的 GOT 访问指令数，再按执行频度加权：

```sh
# 静态：数 GOT 访问指令
objdump -d vmlinux | grep -cE '@GOTPCREL|adrp.*:got:'

# 动态：采样看这些指令的执行占比
perf record -e cycles:k -g -- <负载>
perf annotate --stdio <随机化函数名> | grep -E 'got'
```

> **这一项的意义**：共享 GOT 把全内核的全局变量地址集中到一张表，若这张表被高频访问，
> 它的 cache line 会成为热点，多核下还会互相冲刷。T4 给出"到底热不热"的量级，
> 决定 §5 中"缓存局部性变差"这条弊端是理论隐患还是实际问题。

## 5. `-mcmodel=large` 的弊端（正文应交代的）

1. **代码体积膨胀。** 每个绝对立即数 10 字节，外部调用还多一条间接跳转。由 T2 定量。
2. **I-cache 与 iTLB 压力上升。** 体积膨胀的直接后果，由 T3 定量。**这是最需要实测的一条**，
   因为它可能抵消掉随机化本身的低开销。
3. **多占一个寄存器。** 外部调用需要一个临时寄存器承载目标地址，增加寄存器压力，
   在寄存器紧张的函数里会引发额外的溢出与重填。
4. **直接调用变间接调用。** 间接调用对分支预测不如直接调用友好；同时它与硬件 CFI 的
   交互需要注意（间接转移会受 IBT/BTI 约束，落点必须有标记），这一点与第 5 章相关。
5. **失去链接器松弛优化。** 链接器无法把绝对寻址收紧回 PC 相对寻址。
6. **与内联汇编的约束冲突。** 内核中使用 `"i"`（立即数）约束或依赖特定寻址形式的内联汇编，
   在大代码模型下可能无法满足约束而编译失败，需要逐处适配。
7. **工具链成熟度差异。** GCC 与 Clang 对大代码模型的支持程度与生成质量不同，
   本文两份编译器插件都要覆盖，需在 T2 中分别测。

> **注意范围**：以上代价只施加在**随机化范围内**的函数上，内核其余部分仍用默认代码模型。
> 因此膨胀的分母是随机化范围而非整个内核，正文报告时要写清分母。

## 6. 共享全局偏移表的弊端（正文应交代的）

### 性能侧

1. **缓存局部性变差。** 每模块/每子系统一张表时，访问局部性好；全内核共用一张表后，
   互不相关的子系统访问同一张表的不同部分，互相冲刷 cache line。由 T3/T4 定量。
2. **多核伪共享。** 多个核同时访问同一张表的相邻表项时会争用同一条 cache line。
   表是只读为主（见下）的话争用有限，但仍应在多核负载下观测。
3. **多一次内存引用。** 每次全局变量访问由"直接寻址"变为"先读表项再访问"，
   多一次 load 与一次潜在的 cache miss。

### 安全侧（更要紧，正文必须写）

4. **单点集中泄露。** 一张表集中了随机化代码用到的**全部全局变量地址**。虽然 §3.4.3 的
   优化一已把外部函数地址排除在外（因而读表**不能**直接得到代码布局），但数据地址本身
   仍有价值：内核中若干全局变量正是纯数据攻击的经典目标。攻击者读到这张表，
   等于免去了定位这些变量的功夫。
5. **必须保持可写，因而是篡改目标。** 表在持续随机化过程中要更新，无法长期置为只读。
   攻击者改写某个表项，即可把一次合法的全局变量访问重定向到自己控制的地址，
   这是一条不经过控制流劫持的数据攻击路径。**这条与 §3.7.4 已列的白名单缺口同源**：
   都依赖内核自己维护的页权限，而任意写可以改回权限。
6. **表本身位置固定。** 表不参与随机化（它是随机化的基础设施），因此它的地址是已知的，
   上述两条得以成立。

> **对正文的要求**：§3.7.4「本章机制自身引入的攻击面」当前列了 `target_addr`、白名单、
> 活跃执行流集合三项，**漏了共享 GOT**。应补入，并说明其保护同样依赖第 4 章的只执行内存
> 与页权限，属于本章无法自行封闭的缺口。
