## 6.1 引言

第 3、4、5 章分别给出了持续随机化的执行机制、按需触发机制与非随机化区域的保护机制，并各自验证了机制达到了该章开头列出的设计需求。三项机制单独有效，并不等于三者叠加之后仍然可用：叠加会带来累积的性能开销，机制之间存在参数耦合，而攻击者面对的是三者共同构成的防御体系而非其中任何一项。

本章因此回答一个问题：**三项机制叠加之后，I-KASLR 是否在真实负载下开销可承受，并且能够拦截完整的攻击链。** 全章围绕这一命题组织，具体包括：给出完整原型的工程构成与两个硬件平台的分工（第 6.3 节）；报告编译期静态验证的结果，即本文安全论证唯一可机械验证的那条性质（第 6.4 节）；评估三项机制逐层叠加的端到端开销并作归因（第 6.5 节）；在真实网络与存储负载下与 Adelie、Dbox 同台对比（第 6.6 节）；分析随机化频率与随机化范围两个参数的敏感性（第 6.7 节）；最后以真实 CVE 构造的攻击链验证三项机制的协同防御效果（第 6.8 节）。

本章不重复各机制章已经给出的微观数据。凡涉及单机制的开销分解与机制内部的正确性验证，均引用对应章节。

## 6.2 实验总体安排

本节先给出全部实验的清单与依赖关系，便于对照后续各节。

### 6.2.1 平台分工

第 5 章的机制依赖 ARM 指针认证，第 4 章在 x86 上依赖二级地址翻译、在 ARM 上依赖调试观察点。因此两个平台承担的角色不同：

**ARM 平台是主平台。** 第 3 章的机制跨平台，第 4 章在此走观察点路径且覆盖完整，第 5 章本身即 ARM 机制。三项机制在此平台上构成完整可运行的系统，因此第 6.5 节的叠加开销、第 6.6 节的同台对比与第 6.8 节的攻击链验证均在 ARM 上进行。

**x86 平台用于验证可移植性。** 第 3、4 两章的机制在此运行，第 4 章走二级地址翻译路径。本章在 x86 上只报告两项机制叠加的开销，用以说明前两项工作不绑定架构，并与 ARM 上的对应数字对照。

> **【待核实 R-61】** 上述分工要求 ARM 实验机同时具备指针认证与调试观察点，且能够在无虚拟化层的条件下运行第 4 章的观察点路径。**请尽早确认手头的 ARM 平台满足这些条件**，因为它决定了主平台的选择，而主平台一变，本章大半实验都要重做。需要确认的具体项：处理器是否实现 `FEAT_PAuth`、可用的调试观察点数量与 `MASK` 域的实际位宽、以及在 EL1 数据访问上触发观察点所需的调试授权状态是否可在生产配置下开启。

## 6.4 编译期静态验证

本节报告本文安全论证中唯一可被完全验证的那条性质在完整内核映像上的验证结果。

第 3.5.1 节说明了编译器如何把所有跨区域控制流转移重定向到跳板，第 3.6.5 节给出了在随机化范围内的验证方法。本节把同一验证程序应用于完整的内核映像，以确认不存在遗漏。

## 6.6 真实负载下的对比评估

### 6.6.1 负载与对比方案

真实负载选择网络与存储两类 I/O 密集型场景，理由是这两类负载会频繁进入内核、跨越随机化区域边界，因而最能暴露跳板机制与检测机制的开销。

对比方案包括 Adelie 与 Dbox。

> **【待核实 R-63】关于对比的可比性。** Adelie 保护的是内核模块与驱动，本文保护的是 built-in 内核代码，**两者的保护范围不同，直接比较开销数字是不公平的，而且不公平的方向对本文有利**（本文的范围更大、代价自然更高）。这一点必须在正文中主动说明，并给出一个尽量可比的配置，例如：把本文的随机化范围限制到与 Adelie 相同的模块集合，测一组「同范围」的开销，再单独给出本文在 built-in 范围上的开销。
>
> **只报后者而不作范围说明，会被评委指出比较不对等。** 主动给出同范围的对照，反而能把「范围更大」变成论据。

> **【待核实 R-64】** Adelie 与 Dbox 是否有可用的开源实现、能否在你的 ARM 平台上跑起来？**若无法复现，就只能引用原文的报告数字，那么两者的实验环境不同，比较的说服力会大打折扣。** 请尽早确认，因为这决定第 6.6 节是「同台对比」还是「与文献数字对照」，两者在正文中的写法完全不同。

## 6.8 综合安全性验证

### 6.8.1 攻击链的构造

本节的安全性验证与第 4、5 章的攻击性实验有两处根本差别，需要先说明，否则容易被读成重复。

**第一，攻击者能力的来源不同。** 第 4 章的检测覆盖率（第 4.6.2 节）、触发延迟（第 4.6.5 节）与 gadget 可用性（第 4.6.6 节），以及第 5 章的跨区域劫持拦截验证（第 5.6.6 节），都由一个仅用于评估的含漏洞内核模块直接赋予攻击者任意读写能力。攻击者从威胁模型所设定的起点出发，不需要真的从一个漏洞打进来。这样做是为了把机制的响应与漏洞利用本身的偶然性分开，使参数扫描成为可能。**本节则从一个真实的内核漏洞出发**，攻击者必须自己完成从触发漏洞到获得原语的全过程。

**第二，验证的粒度不同。** 前两章验证的是单个机制对单类攻击行为的响应，例如「读取代码是否被检测到」「伪造的跨区域转移是否被拒绝」。本节验证的是三项机制对一条完整攻击路径的协同拦截，即攻击者依次尝试泄露、定位、构造、劫持、提权时，每一步分别在哪一档配置下被哪个机制挡住。**只有在完整链条上才能看出机制之间是否存在缝隙**：单独测试各自通过，并不排除攻击者绕开其中一项、从另外两项之间的空隙穿过去。

> **【待核实 R-65】漏洞的选取。** 建议从第 1.2 节统计出的「只能内建」类 CVE 中挑选，并且落在本文随机化范围覆盖的子系统内。这样攻击链验证与第 1.2 节的问题陈述形成闭环：**开篇论证的盲区，正是最后被拦截的攻击所在之处。**
>
> 第 1 章已核实脏牛（`mm/gup.c`）与脏管道（`fs/splice.c`）都属于只能内建的代码，二者的公开利用程序也较易获得，是可以优先考虑的候选。**请确认这两个漏洞对应的子系统是否在你的随机化范围之内**，若不在，需要把范围扩到覆盖它们，或者另选漏洞。

### 6.8.2 攻击链拦截矩阵

把攻击链分解为若干步骤，逐步标出在各档配置下被哪个机制拦截。

**表 6-4　攻击链拦截矩阵**

| 攻击步骤 | 对应向量 | Base | +R | +RD | +RDP |
| --- | --- | :-: | :-: | :-: | :-: |
| 触发漏洞获得任意读写 | — | 成功 | 成功 | 成功 | 成功 |
| 读取代码收集 gadget | V1 | 成功 | | | |
| 由代码索引推断布局 | V3 | 成功 | | | |
| 执行试探定位 gadget | V2 | 成功 | | | |
| 构造并触发跨区域劫持 | V4-B | 成功 | | | |

>
> 逐列填写的意义在于**显示每个机制各自拦住了哪一步**，而不只是给出最终「攻击失败」这一个结论。若某一步在 +RDP 下仍然成功而攻击最终仍然失败，也要如实标注，并说明是后续哪一步拦住的。

### 6.8.3 攻击者可用资源的收敛

除了「是否被拦截」这一二值结果，还需给出攻击者在被拦截之前实际获得了多少资源。

> **【待补 W-73】** 三组数据，均报告分布而非均值：拦截前攻击者获得的 gadget 数量（与第 2.1.2 节表 2-1 的静态基线对照）；触发拦截所需的探测次数；从首次探测到拦截的时间。**报告分布区间的理由是安全性由最坏情况决定**，均值会掩盖尾部。

### 6.8.4 地址有效期

第 2.2.3 节已说明，本文机制不减少镜像中 gadget 的数量，改变的是它们的地址在运行时是否稳定。因此安全性评估的核心指标是**地址的有效期**，即一个被泄露的代码地址从泄露到失效之间的时长。

> **【待补 W-74】** 测量方法：在攻击链执行过程中记录每一个被泄露的地址及其失效时刻，给出有效期的分布。与第 1.1.5 节引用的 1.5 至 3.5 秒间隔上界对照。**这一指标比 gadget 计数更贴近本文的防御原理**，建议作为第 6.8 节的主要结论指标。

## 6.9 开销来源归因

把第 6.5 节测得的端到端开销拆回到具体来源，包括跳板引入的间接跳转、执行流追踪的计数操作、白名单查询、检测机制的异常处理、随机化本身的暂停与迁移、以及指针认证指令。

> **【待补 W-75】** 建议用性能计数器或采样剖析给出各来源的占比，并与第 3.6.3 节、第 4.6.4 节、第 5.6.4 节的微观测量对照，说明二者是否吻合。**若端到端开销显著高于各微观开销之和，需要解释差额来自何处**，例如缓存局部性的损失或页表压力，这类二阶效应只有在系统级才观察得到，如实报告反而是本章的价值所在。

## 6.10 讨论

**范围之外的开销来源。** 本章测得的开销以本文选定的随机化范围为前提。范围扩大到更多子系统时，开销如何变化由第 6.7.2 节的曲线给出趋势，但曲线之外的外推不在本文的实验支持范围之内。

**长期运行的行为。** 本章的实验时长有限，未能覆盖长期运行下的行为，例如地址空间碎片化、跳板表的增长、以及高扇入函数集合是否会持续扩大。

> **【待核实 R-66】** 上一点值得实测一次：**跑一个数小时到数天的长时间负载，观察随机化区域的地址空间占用、跳板表规模与触发频率是否随时间漂移。** 这个实验不难做（挂一个负载生成器让它跑着即可），但很能说明系统的工程成熟度，也能提前发现内存泄漏一类的问题。建议在别的实验做完之后挂上去跑。

**与内核既有机制的共存。** 第 3.8 节已列出与 `ftrace`、`kprobes`、栈回溯、`livepatch` 的适配问题。本章的实验在这些设施关闭的条件下进行。

> **【待核实 R-67】** 若最终的适配方案是「本文机制与这些设施互斥」，需要在本章明确说明实验配置，并在讨论中承认这一限制；若适配方案是可共存，则应补一组开启这些设施后的开销数据。**这个选择要早做，因为它影响实验配置。**

## 6.11 本章小结

本章给出了 I-KASLR 完整原型的工程构成与两个平台的分工，报告了跨区域控制流转移的静态验证结果，评估了三项机制逐层叠加的端到端开销，在真实网络与存储负载下与已有方案作了对比，分析了随机化频率与随机化范围两个跨章参数的敏感性，并以真实 CVE 构造的攻击链验证了三项机制的协同防御效果。
